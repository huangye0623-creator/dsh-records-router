# 记录路由器：按指令定位档案，不整读上下文

> 中文 | [English](records-router.en.md)

> 问题：工作区里堆了交接记录、归档、项目文档、报告；每次都要读全部吗？
> 目标：**先判断你的问题涉及哪些方面，再只读命中的 3~6 段（文件:行号）**。

---

## 1. 为什么不直接用 grep / 向量库

| 方案 | 问题 |
|---|---|
| `grep` 关键词 | 只能精确匹配；不懂“主题/项目/别名”；结果没有排序和阅读预算 |
| 全量向量库 | 要嵌入模型/服务/数据库；对几十万字本地文档过重；中文分词也要处理 |
| 全读进上下文 | 贵、慢、还容易被截断 |

记录路由器走中间路线：**标题级索引 + 轻量打分 + 行号回读**，零外部依赖。

## 2. 索引什么

默认只索引“记录类”文件，不索引工具/缓存目录：

- `当前状态.md`、`交接记录.md`、`交接归档/*.md`
- 规则文件（如 `AGENTS.md`、规范文档）
- 说明文件（`使用说明.txt`）
- 交付文档目录（`03_产出/*.md`、项目内的 `03_产出/**`、项目说明/交接文件）

按 Markdown 标题切段，记录：

```json
{
  "kind": "当前状态",
  "project": "项目A",
  "title": "进行中",
  "file": "<workspace>/当前状态.md",
  "start": 10,
  "end": 19,
  "date": "2026-10-22",
  "preview": "……前 400 字……"
}
```

## 3. 打分（够用即可）

查询分词：

- 英文按单词；
- 中文按**连续片段 + 2-gram**（“交接记录”→“交接记录 / 交接 / 接记 / 记录”），避免依赖分词库；
- 主题别名表（`topics.json`）把“项目别名/简称/英文名”扩展进来。

打分类似轻量 TF-IDF：

- 标题命中权重最高，项目名次之，正文最低；
- 用 **IDF** 降低高频词（“项目”“文件”）的影响；
- **覆盖率**加成：命中查询词越多，越贴题；
- 短语命中（连续词）额外加分；
- 类型权重：当前状态/最近交接 > 归档/规则；
- 意图加成：问“之前/为什么”→ 归档；问“现在/下一步”→ 当前状态。

然后按预算截断：默认**最多 6 段 / 400 行**，保证“路由完不会又变成整读”。

## 4. 命令

```bash
# 1) 建索引
python examples/records-router/records_router.py build

# 2) 按原话查询（输出：主题入口 + 必读基线 + 命中段表）
python examples/records-router/records_router.py query "项目A 下一步要确认什么"

# 3) 只读命中的第 1、2、3 段
python examples/records-router/records_router.py read 1 2 3

# 4) 维护
python examples/records-router/records_router.py stats
```

输出示例（匿名化）：

```text
识别到：项目A
主题入口：<workspace>/项目01_项目A
必读基线：当前状态.md（约 30 行）
| # | 类型 | 位置 | 标题 | 分数 |
| 1 | 当前状态 | 当前状态.md:10-18 | 进行中 | 80.5 |
| 2 | 项目文档 | 方案.md:1-9 | 方案标题 | 52.9 |
| 3 | 交接条目 | 交接记录.md:22-31 | 2026-10-22 · … | 40.0 |
```

## 5. 技能封装

把“先路由再读”写成一个技能（`SKILL.md`），让 AI 在涉及历史/项目/交接时**自动先跑命令**：

- 触发词：项目名、“之前/为什么/进展/下一步”、交接/归档/记录；
- 硬规则：**禁止整读** `交接记录.md` 或归档；先 query 再 read；
- 兜底：无命中时先读 `当前状态.md`，再 `grep`。

示例见 `examples/records-router/SKILL.md`。

## 6. 实测数字

| 指标 | 数值 |
|---|---|
| 索引规模 | 82 个文件 / 1535 段 |
| 单次查询 | 约 0.4 秒（含索引新鲜度检查） |
| 单次实际阅读 | 3~6 段，约 50~130 行 |
| 索引保鲜 | 查询前比对源文件 mtime，有变化自动重建 |

对比：改版前一次“相关排查”要读 1000+ 行的交接记录/归档；现在默认只读命中段。

## 7. 局限与升级路线

**当前局限**

- 基于关键词/IDF，**不懂语义**（同义改写可能漏）；
- 中文没有词性/实体识别，靠 bigram 近似；
- 标题切分依赖文档结构（没有标题的文档效果差）；
- 索引是本地 JSON（1500 段约 1 MB），更大规模需要换存储。

**升级路线（按投入从低到高）**

1. **BM25**：补上词频/长度归一化，排序更稳；
2. **SQLite FTS5**：自带全文索引，但中文需要分词/trigram；
3. **本地小嵌入模型**：语义召回 + 关键词召回混合（hybrid）；
4. **现成方案**：`ratel`（BM25+语义、无向量库）、`basic-memory`（Markdown 知识图谱）、DSH 记忆插件（自动注入，另一条路线）。

## 8. 什么时候不该用它

- 只有几份小文档：直接读更快；
- 需要“自动记住”而不是“按需查”：用自动记忆插件；
- 需要跨语言/语义检索：上嵌入或专用检索服务。
